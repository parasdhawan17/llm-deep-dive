MODULE 4

Choosing a Model

This module teaches you how to choose a model for your task. You will learn what benchmarks can and cannot tell you. You will learn how to test models on your own real work. You will learn how to balance cost, speed, and quality.

Lesson 4.1

Benchmarks and their limits

A benchmark is a standard test. It measures one skill of a model.

Tests you will see

  • MMLU tests school knowledge. It uses multiple-choice questions. It covers subjects like math, history, and law.
  • HumanEval tests code writing. The model reads an English description. It then writes a short program.
  • Other tests measure math word problems, logical reasoning, or chat quality.

Why a high score can mislead you

Your task is not the test. Real inputs are messy and unclear. Test questions are clean and short. A model can win the test and still fail your task.

  • The test style differs from your work.
  • Your users write unclear prompts.
  • Your data has private terms the test never saw.
BenchmarkWhat it measuresIts limit
MMLUSchool knowledge, multiple choiceReal tasks are not multiple choice
HumanEvalShort code from descriptionsReal code needs large context
Chat testsHuman preference votesVotes favor long, confident answers

Contamination and gaming

Contamination means the test questions were in the training data. The model then repeats memorized answers. The score looks high. The true skill is lower.

Gaming means training for the test itself. Builders tune prompts and data for one benchmark. The score rises. Real quality does not rise.

Note: A high score proves skill on that test only. Test the model on your own task before you decide.

Lesson 4.2

Evaluate on your own workload

An eval set is a small group of real examples from your work. Each example has an input and the correct answer.

Build the eval set in six steps

  1. Collect 50 to 200 real inputs from your users.
  2. Write the correct answer for each input.
  3. Run every candidate model on the same inputs.
  4. Score each answer as correct or wrong.
  5. Measure speed and cost for each model.
  6. Choose the model with the best balance for you.

What to measure

MetricMeaningHow to measure
QualityShare of correct answersCorrect answers divided by total answers
LatencyTime per answerSeconds from request to full answer
CostMoney per taskTokens used times price per token
quality = correct answers / total answers
cost per 1,000 tasks = tokens per task x price per token x 1,000

Human review or LLM-as-judge

An LLM-as-judge is a strong model that grades answers. Human review is slow. It is the most trusted method. Use it for final decisions. LLM-as-judge is fast. It can favor answers in its own style. Use it for quick first checks.

Note: Test all models with temperature 0. This removes random change. Your comparison stays fair.

Check your understanding

  2. When do you use human review instead of LLM-as-judge?
  3. Write the formula for quality.
Hints1. Same inputs make the test fair; different inputs would change the result. 2. For final decisions, where trust matters most. 3. Correct answers divided by total answers.

Lesson 4.3

Cost, latency, and quality trade-offs

You cannot have the best of all three. You must choose your balance.

Token prices

You pay for each token you send. You pay for each token the model writes. Output tokens usually cost more than input tokens. Long answers cost more than short answers.

Speed

Speed means tokens per second. Small models usually write faster than large models. First-token delay also matters for chat.

When a small model wins

  • The task is simple, for example text labels or short summaries.
  • You run millions of tasks and cost matters.
  • Users need answers in under one second.

When you need a frontier model

A frontier model is the strongest public model of its time.

  • The task needs hard reasoning or long documents.
  • A wrong answer costs you money or trust.
  • The task needs rare knowledge the small model lacks.
Your needBest choice
Simple repeated tasksSmall model
Hard reasoningFrontier model
Tight budgetSmall model
High cost of errorFrontier model
Note: Start with a small model. Move to a larger model only when your tests prove you need it.
